### A-2. 기간 일정 표시 규칙 (2026-07-29 sun 확정)

**설계 원칙: 표시 하나가 질문 하나만 답한다.** 지금은 배지·책갈피·상태 라벨이 모두 "급함"을 말하려 해서 서로 부딪히고 있음. 역할을 갈라놓는 것이 이 작업의 핵심.

| 표시 | 답하는 질문 |
| --- | --- |
| 원 안의 숫자 배지 | 이 날 **손을 움직일 일**이 몇 개? |
| 초록 선 | 언제부터 언제까지 **열려 있나**? |
| 책갈피 | **마감까지** 며칠? |
| 상태 라벨 (`event-card__status`) | **지금 무슨 상태**? |

**규칙 1 — 초록 선.**
시작일은 숫자 아래 중앙에서 오른쪽으로, 마감일은 왼쪽에서 숫자 아래 중앙까지, 중간 날은 칸을 가로지름. 두께 2px, 색은 기존 `--dw-success`(#33765d) 재사용. `.calendar-grid`의 `gap: 2px` 때문에 칸 사이에서 선이 끊겨 보이므로 선을 양쪽으로 2px씩 넘겨 메움. 주가 넘어가면 토요일 칸 끝까지 → 다음 줄 월요일부터 다시 시작.

**규칙 2 — 배지는 시작일·마감일에만.**
기간 중간 날은 숫자에서 제외하고 선만 그림. 선이 이미 "진행 중"을 말하므로 숫자로 또 말하면 중복이고 숫자만 불어남. 배지 = 그 날 시작하거나 마감되는 일정 수. 3일짜리 하나가 3일 내내 "1개"를 만드는 원래 문제도 이걸로 함께 해소됨. **배지 색 규칙(마감 초과 / 3일 이내 / 그 외 / 완료)은 건드리지 않음.**

**규칙 3 — 책갈피는 항상 마감 D 표시, "진행중"은 상태 라벨로.**
책갈피를 초록 "진행중"으로 바꾸면 마감일 당일에 빨간 D 표시가 초록으로 변해서 **가장 급한 날이 가장 안 급해 보임**. 앱 미션("아 맞다!" 없애기)과 정면으로 어긋남.
그래서 둘 중 하나를 고르는 대신 자리를 나눔 — 책갈피는 마감 D 표시를 유지하고, 기간 안이면 상태 라벨을 "진행중"(연한 초록 `--dw-success-soft` 배경 + 진한 초록 글씨)으로 표시. 이러면 여행이든 마감형 과제든 둘 다 정확해짐: 마감일에 `D-day` + `진행중`이 같이 뜨고 마감이 가려지지 않음.
상태 라벨은 `.event-card__status--{level}` 색 체계가 이미 있어서 초록 한 종류만 추가하면 됨.

**규칙 4 — 선택한 날짜 패널.**
헤더 왼쪽에 `8월 13일 목요일 · 내일`(오늘/내일/모레는 그 말로, 그 외엔 `N일 뒤`), 오른쪽에 `진행중 N개 · 일정 N개`. 진행중 개수는 초록. 진행중 카드를 목록 맨 위로 정렬.
헤더에 오늘 기준점을 박는 이유는 A-5 참고.

### A-3. 러닝엑스 과제는 starts_at이 없어서 선이 안 생김

- **현재 상태**: `src/lib/canvas/mapping.ts:66` — 과제는 `starts_at: null`로 저장. 캘린더 이벤트(89행)만 `start_at`을 넣음.
- **문제**: 기간 선 기능을 만들어도 **러닝엑스 과제에는 한 줄도 안 그려짐.** 직접 입력과 공지 분석 일정만 혜택을 봄. 기능 체감이 거의 없을 수 있음.
- **결정 필요**: Canvas 과제의 `unlock_at`(공개 시각)을 `starts_at`으로 쓸지. 쓰면 "이번 주 내내 열려 있는 과제"가 선으로 보이지만, unlock_at이 학기 초로 잡힌 과제는 선이 몇 달짜리로 늘어짐 → 상한(예: 14일)이 필요할 수 있음.

### A-4. dashboard/page.tsx가 580행, 날짜 규칙이 페이지 안에 박혀 있음

- **문제**: `eventOccupiesDay`, `getCalendarDayStatus`, `getDeadlineBookmarkLabel`이 서버 컴포넌트 파일 안에 있어서 vitest로 단위 테스트가 안 됨. 반면 `src/lib/schedule-sections.ts`(55행)는 분리돼 있고 테스트가 있음.
- **할 것**: 기간 선/진행중 판정 로직을 `src/lib/calendar-span.ts` 같은 파일로 빼고 테스트 추가. 날짜 경계(KST 자정, 월 넘어감, 주 넘어감)는 눈으로 확인하기 가장 어려운 부분이라 테스트 가치가 큼.

### A-5. D-day 계산 버그 — 별도 PR로 분리 (캘린더 작업 아님)

`src/app/dashboard/page.tsx`의 `getDeadlineBookmarkLabel`(145행)이 밀리초 산수를 쓰고 있음.

```ts
if (remaining <= DAY_IN_MS) return "D-1";
```

**버그 1 — 오늘 마감이 `D-1`로 뜸.** 오늘 12일 14:00에 마감이 12일 23:59면 10시간 남았으니 `D-1`. 내일 아침 마감(20시간 남음)도 똑같이 `D-1`. **오늘 것과 내일 것이 같은 글씨로 뜸.**

**버그 2 — `D-day`가 코드에 아예 없음.** `D+N`과 최소 `D-1`만 존재. 그런데 온보딩(`src/app/OnboardingCarousel.tsx:20`)에서는 "D-day 표시와 마감 6시간 전 알림으로…"라고 약속하고 있음. 약속한 표시가 한 번도 안 뜸.

**고치는 법**: 남은 시간(밀리초)이 아니라 **KST 날짜 차이**로 계산. 오늘 마감 = `D-day`, 내일 = `D-1`, 모레 = `D-2`. 한국 사용자가 D-day를 읽는 방식과 일치하고, 시각이 아니라 날짜로 세니 경계 애매함이 사라짐.

**혼란 하나 더** — 오늘이 12일인데 캘린더에서 13일을 누르면 카드에 `D-1`이 뜸. 화면은 "8월 13일"이라고 말하는데 D는 오늘 기준이라 서로 싸움. D 계산을 건드리는 대신 **헤더에 기준점을 박아서** 해결(A-2 규칙 4). `8월 13일 목요일 · 내일`이라고 먼저 읽히면 카드의 `D-1`이 같은 문장의 일부로 자연스럽게 붙음.

**왜 별도 PR인가**: D 표시는 모든 카드에 쓰이므로 목록 화면 전체가 바뀜. 푸시 알림 4단계(`src/lib/reminders.ts`)와 말이 맞는지도 확인해야 함. 캘린더 선 작업과 섞으면 문제가 생겼을 때 원인을 가릴 수 없음.
**할 것**: `getDeadlineBookmarkLabel`을 `src/lib/`로 빼고 테스트 추가(오늘 23:59 마감 → `D-day`, 자정 직전/직후, 월말 넘어감).

## D. 출시 전 보안 (미룰수록 위험이 커짐)

### D-1. 키들이 채팅에 노출된 상태

- **재발급 필요**: `SUPABASE_SECRET_KEY`(최우선), `GEMINI_API_KEY`, VAPID 키 3종.
- **주의**: `TOKEN_ENCRYPTION_KEY`를 바꾸면 **이미 저장된 Canvas 토큰이 전부 복호화 불가**가 됨(AES-GCM). 바꿀 경우 재연결 안내가 필요하니 순서를 정해야 함.
- **VAPID를 바꾸면** 기존 푸시 구독이 전부 무효화됨 → 사용자가 알림 재허용해야 함. 출시 전에 하는 게 맞음.

- **할 것**: 개발 끝나면 e-Campus에서 삭제.
