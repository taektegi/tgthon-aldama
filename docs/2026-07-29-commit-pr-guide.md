## 3. 커밋 — 세 덩어리로 나눈다

**왜 나누나**: 커밋은 "되돌리기 단위"다. 한 덩어리에 다 넣으면 나중에 캘린더만 되돌리고 싶어도
개명까지 같이 날아간다. 서로 다른 이유로 바뀐 것은 따로 담는다.

### 커밋 1 — 앱 이름 개명

  src/app/layout.tsx src/app/page.tsx src/app/login/page.tsx \
  src/app/signup/page.tsx src/app/settings/page.tsx \
  src/app/welcome/page.tsx src/app/connect/learnx/page.tsx \

```

### 커밋 2 — 캘린더 기간 띠와 D 표시

```bash
git add src/app/dashboard/page.tsx src/app/globals.css \
  src/lib/calendar-span.ts src/lib/calendar-span.test.ts \
  src/lib/deadline-label.ts src/lib/deadline-label.test.ts

```

### 커밋 3 — 문서

```bash
git add docs/
git commit -m "docs: 열린 문제 정리와 커밋·PR 절차 문서 추가"
```

**`git add`는 왜 필요한가**: git은 "바꾼 것"과 "이번에 담을 것"을 구분한다. 장바구니에 담는 게 `add`,
계산하는 게 `commit`이다. 담지 않은 물건은 계산되지 않는다.

확인:

```bash
git log --oneline -3
git status
```

`git status`가 깨끗해야(nothing to commit) 다 담긴 것이다.

## 5. PR 만들기

### PR이 뭔가

Pull Request = "내 브랜치를 main에 합쳐 달라는 요청서". 세 가지 일을 한꺼번에 한다.

1. **변경 내용을 보여준다** — 어떤 파일의 어느 줄이 바뀌었는지 GitHub가 나란히 보여준다
2. **자동 검사를 돌린다** — Netlify가 deploy-preview를 만들어 실제 배포된 화면을 미리 볼 수 있게 한다
3. **대화 기록을 남긴다** — 왜 이렇게 했는지, 무엇을 논의했는지가 저장된다. 나중에 "왜 이 코드가 이렇지?"의 답이 된다

**중요**: PR을 만들어도 main은 아직 안 바뀐다. `merge`를 눌러야 바뀐다. 그래서 PR은 안전하다 —
만들어놓고 며칠 방치해도 아무 일도 안 일어난다.

### PR 본문 파일 만들기

터미널에 긴 글을 직접 쓰기 어려우니 파일로 만들어 넘긴다. 아래를 **한 덩어리로** 복사해 붙여넣는다.

```bash
cat > /tmp/pr-body.md <<'EOF'
## 무엇을 바꿨나

### 1. 캘린더: 기간 일정을 제목이 적힌 띠로 표시

시작과 마감이 둘 다 있는 일정(여행·행사·신청 기간 등)을 제목이 적힌 띠로 그린다.
마감만 있거나 시작만 있는 일정은 지금처럼 숫자 배지로 남는다.

- 띠는 여러 칸을 덮는 하나의 요소라서 날짜 칸 안에 넣을 수 없다.
  그래서 주마다 칸 위에 겹치는 별도 층(`.calendar-week__bars`)으로 그리고,
  클릭은 아래 날짜 칸이 받도록 `pointer-events: none`을 준다.
- 주가 넘어가면 조각을 새로 만들고 제목을 다시 적는다. 이어지는 쪽은 각지게,
  진짜 시작·끝은 둥글게 깎고 3px 물러나 "여기서 끝났다"가 분명하게 보이도록 했다.
- 겹치는 기간은 서로 다른 줄에 놓는다(`assignSpanLanes`). 칸 높이를 66px → 86px로 키워
  세 줄까지 겹침 없이 들어간다. 그보다 많으면 칸에 `+N`으로 알린다.
- 지금 진행 중인 기간은 진한 초록, 아직 시작 안 한 기간은 연한 초록.
  카드의 `진행중` 라벨과 같은 `isInProgress` 판정을 써서 캘린더와 카드가 항상 같은 말을 한다.

### 2. 배지 규칙 정리

배지는 "이 날 끝내야 할 게 몇 개"만 센다(`countsInBadge`).
기간 일정의 시작일과 중간 날은 세지 않는다 — 띠가 이미 알려주기 때문이다.

이전에는 3일짜리 일정 하나가 3일 내내 "일정 1개"를 만들어 "3일 연속 마감"으로 읽혔다.
배지 색도 마감의 급함만 말하게 정리했고, 오늘 마감이 있는 날은 빨간 배지를 새로 넣었다.

### 3. D 표시를 달력 날짜 기준으로 (버그 수정)

기존 `getDeadlineBookmarkLabel`은 밀리초 산수를 썼다.

```ts
if (remaining <= DAY_IN_MS) return "D-1";
```

이 때문에 **오늘 밤 마감(10시간 남음)과 내일 아침 마감(20시간 남음)이 둘 다 `D-1`** 이었고,
`D-day` 문자열은 코드에 아예 없었다. 그런데 온보딩(`OnboardingCarousel.tsx:20`)은
"D-day 표시와 마감 6시간 전 알림으로…"라고 약속하고 있었다. 약속한 표시가 한 번도 안 떴다.

`src/lib/deadline-label.ts`로 분리하고 KST 달력 날짜 차이로 계산한다.
오늘이면 `D-day`, 내일이면 `D-1`, 지났으면 `D+N`.

**세는 대상도 시작 시각으로 갈린다.** 시작 전이면 시작까지, 시작 시각이 지나면 마감까지.
그래서 시작도 안 한 5일짜리 일정에 "진행중"이 붙지 않는다.
기준이 바뀔 때 숫자가 커져 헷갈리므로 책갈피에 `시작까지` / `마감까지`를 작게 적었다.

카드 배경색과 상태 문구는 그대로 시간 기준(`urgency.ts`)이다. 건드리지 않았다.

### 4. 선택한 날짜 표시

칸을 칠하는 방식을 버리고 날짜 숫자를 진한 원으로 바꾼다.
칸을 칠하면 어떻게 칠해도 띠와 같은 공간을 다퉜다 — 연회색이면 연한 띠와 헷갈리고,
검정이면 띠를 깔아뭉개고, 흰 막이면 비활성처럼 보였다.
숫자가 있는 왼쪽 위는 띠가 절대 닿지 않는 자리다.

## 7. 머지

Taeksoo 확인이 끝나면:

```bash
git fetch origin          # 그 사이 main이 또 바뀌었는지 확인
gh pr merge --merge
```

**왜 `--merge`인가**: 세 가지 방식이 있다.

- `--merge`: 커밋 3개를 그대로 main에 붙이고 "합쳤다"는 커밋을 하나 더 만든다. 기록이 가장 정직하다
- `--squash`: 커밋 3개를 1개로 뭉갠다. 기록이 깔끔하지만 되돌리기 단위가 사라진다
- `--rebase`: 커밋을 main 끝에 옮겨 붙인다. 기록이 일자로 예뻐지지만 손이 많이 간다

이 프로젝트는 `--merge`를 쓰기로 했다.

머지되면 **Netlify가 main을 자동으로 배포한다.** 몇 분 걸린다.

## 막혔을 때

| 증상 | 원인과 해결 |
| --- | --- |
| `index.lock` 오류 | `rm -f .git/index.lock` |
| vim이 떠서 못 나감 | 영어 입력 모드 → `Esc` → `:wq` → `Enter` |
| `push`가 거부됨 | 원격이 앞서 있다. `git fetch origin` → `git merge origin/main` → 다시 push |
| 커밋 메시지를 잘못 씀 | 아직 push 전이면 `git commit --amend -m "새 메시지"` |
| 파일을 잘못 담았음 | `git restore --staged <파일>` (장바구니에서 빼기, 수정 내용은 그대로) |
| dev 서버가 내 수정을 못 알아챔 | `rm -rf .next` 후 재시작 |
